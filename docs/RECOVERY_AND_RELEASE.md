# Recovery and release control
## Application archive V2
The encrypted per-tenant archive is not a full database backup. Configure LUMO_BACKUP_KEY_HEX as a cryptographically random 32-byte key encoded as 64 hex characters using deployment secrets. Never commit it, print it, or use a predictable value. Preserve it in an independent secret manager: losing it prevents decryption. Key rotation and backward key IDs are not implemented yet. Automatic remote upload is opt-in via LUMO_AUTO_BACKUP=true, Firebase storage credentials/bucket and stored owner schedule. Run status STORED means the provider returned successful upload, not verified recovery. No automatic deletion of remote archives. Define retention/access policy in provider configuration. Manual logical archive caps: 5 MiB plaintext and 20,000 total rows. Legacy CTR exports are rejected; handle those offline with authorized operators and treat them as potentially unauthenticated. If the old key was unset or credentials were ever committed, investigate exposure and rotate affected secrets.
## Full PostgreSQL recovery
The commercial backend workflow creates a PostgreSQL 16 dump from its isolated synthetic test database, restores into a second disposable database, checks row counts in core tables and verifies audit triggers. It never uses production credentials and never uploads the dump.
For production: use the managed PostgreSQL provider's backup/PITR or authorized pg_dump; encrypt and store independently of the application, record checksum, recovery point and migration version; test restore in an isolated restricted database with external emails/cron disabled. Validate foreign keys, journals, stock, cash, debt balances, sequence values, permissions and all migrations. Reconcile existing historical transactions; have a second authorized reviewer approve cutover. Never restore directly over the running production database. Establish measured RPO/RTO before commercial launch.
## Release gate
The backend workflow emits a validation manifest with commit SHA, workflow run, package version and migration hashes after tests and recovery drill. It is evidence of backend validation only, not proof of frontend or deployment readiness. Require the separate commercial UI checks, visual acceptance, staging migration and backup verification before merging. Production deployment/rollback remains a separate authorized operation; no automatic deployment enabled.
