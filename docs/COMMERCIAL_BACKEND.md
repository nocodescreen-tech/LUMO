# Commercial backend hardening — phase 1
- Scoped product/client/supplier references, row locking, server-authoritative sale pricing, purchase transaction, field allowlists, authenticated sockets, single-use MFA challenge, revoked refresh rejection and OTP throttling.
- Bulk sales purge and permanent purchase deletion are blocked until audited reversal workflows exist. Payment types restricted to current POS cash/credit.
- No migration or production deployment. Remaining: actual integration tests with isolated PostgreSQL, cash reconciliation, cancellation and refunds ledger, decimal migrations, idempotency, permissions review, CSRF, backups and AI tools, organization model and subscriptions.
- Existing sessions without session IDs will need to authenticate again. Production CLIENT_URL must explicitly contain the trusted frontend origin.

Phase 2: serialized cash open/close, stored cash totals, transactional debt settlement, restricted refunds and no permanent financial deletion; received purchases update inventory, pending/shipped purchases do not. Pending orders need a dedicated receiving workflow. Historic open sessions require reconciliation. Cache scoped by user/role/permissions. Server lockfile currently stale: CI uses npm install as a temporary workaround. Do not deploy until PostgreSQL integration tests pass.

Phase 3: public registration no longer grants superadmin; provision platform admins out-of-band. OTP expiry persisted without migration; old email verification codes must be resent. Password reset invalidates sessions. Backups exclude auth secrets; restore and impersonation temporarily blocked. AI read only and admin-only until permission and confirmation workflows. Action permissions tightened. These safeguards require integration testing and UI compatibility updates before release.

Phase 4: add PostgreSQL 16 CI service with dedicated local test database; integration coverage for tenant isolation, manipulated prices, rollback, concurrent registers, currency, credit settlement, purchase receipt and payment, revoked sessions. Purchase status transitions are forward-only and legacy orders require stock reconciliation. Notifications emitted only after commit. No production database is touched.

Phase 5: explicit versioned migrations, DECIMAL columns and historical currency snapshots, tenant-scoped operation receipts for sale/purchase/debt requests providing an idempotency key, transaction-bound balanced journal postings for sales, inventory costs, purchase receipt/payment, cash refunds and debt payments. Historical records are not fabricated; manual reconciliation and a fresh-install baseline remain. This is a partial financial ledger, not a certified complete accounting system. No production migrations executed.

Phase 6: POS, purchases and debt UI use keyed financial requests with actor-scoped sessionStorage digests; no automatic replay of the unscoped legacy offline queue. No raw payload persisted in the new helper. Offline validation is intentionally disabled until a tenant-bound durable outbox exists. Fixed debt conversion direction. Added operation status endpoint, non-admin sales cost redaction, search permissions, activity pagination bounds and durable logout session revocation. Financial dashboards restricted to owners pending safe role-specific projections. Existing non-admin dashboard and offline UX require redesign.

Phase 7: added an operational expense backend, same-session expense reversal, validated payroll cash outflow and journal postings, finance trial balance endpoint, database trigger preventing journal row updates/deletions, tests for idempotency, foreign staff and cash sufficiency. Expense and payroll UI are not yet redesigned; payroll reversals and full accounting reports remain outstanding. The balance covers only new V2 postings; historical opening entries require reconciliation.

Phase 8: additive organization, branch and warehouse registries; owner-scoped APIs and transaction-locked provisional quota checks; 14-day trial on first workspace access; audited manual subscription grants by superadmins, no charges, no payment verification claims. Existing business transactions continue on the legacy tenant key; branches and warehouses are metadata only until inventory, cash and access scoping migrate. No billing enforcement on existing workflows. Permanent platform user deletion blocked pending retention procedures. Tests added for quota concurrency, cross-tenant warehouse creation and manual grant authorization.

Phase 9: journal-backed income and cash-flow report APIs with explicit incomplete historical coverage, date validation and tenant filtering. Cash closing requires an actual counted balance and explanation for differences. Shared 5DEV orange/neutral palette applied to shell tokens, landing and auth; full visual redesign deferred. No claim of WCAG certification or full accounting compliance.

Phase 10: finance query placeholder spacing corrected; platform console paginated accounts/audit and measured overview, redacted user listings, explicit suspension reason and session revocation, restricted settings, broadcast confirmation, no manual email verification or destructive actions. Billing revenue/MRR deliberately unavailable pending verified payments.

Inventory phase: global Product.stock remains the total; per-warehouse allocations are subsets, unallocated stock is calculated, not duplicated. Owner-only transfer API with idempotency and serialized product/owner locks; DB guards prevent over-allocation or stock below allocated quantities. Sales and receipts may explicitly select a warehouse as owner; legacy flows consume/receive unallocated stock. Refunds restore original warehouse. Warehouse roles, branch cash, lots, serials and physical counts remain outstanding. No automatic historical distribution.

Inventory UI: owner workspace and inventory navigation, paginated product allocation, location creation, transfer history and keyed transfer modal. Existing POS displays unallocated availability, warehouse selection currently API-only for sales and purchases; no warehouse-level cashier permissions or cash separation yet. Bulk import fields allowlisted.

Physical counts: owner-only, single-product immediate reconciliation with explicit expected quantity, counted quantity, reason and idempotency key; stale quantities rejected, global stock and location balance updated transactionally, gain/loss journal at current catalog purchase cost and exchange rate, immutable count history. This is not yet a multi-line count session, approval workflow, cost-layer valuation, or movement freeze. Product catalog supports owner warehouse availability.

Frontend phase: owner-only warehouse selection for POS and purchase receipt, paginated POS catalog using server-provided availability, refresh after sale, cart cleared on account change or POS remount to avoid cross-location stale baskets. Physical count panel records one product/location at a time and displays immutable history. UI in French; browser acceptance still required.

Lot tracking: registering existing stock creates identified subsets without increasing total. Once any lot exists, sales use only identified unexpired lots, ordered FEFO then FIFO for undated lots; refunded sales restore original lot quantities. Transfers of untracked stock cannot consume lots; dedicated lot transfers and disposal with loss journal are provided. Physical count and direct quantity edits for tracked products are blocked until lot-aware count workflow. Reorder rules calculate available sellable stock. Expiration uses Africa/Kinshasa day. Purchase receipts are still manually allocated to lots, not automatically lot-coded. Serial/IMEI, notifications and true FIFO accounting cost layers remain out of scope.

Lot UI: code/expiry search, expired and 30-day filters, registration with existing product lookup, lot-specific transfer and disposal, movement history and configurable per-location reorder thresholds. No background notification delivery or serial/IMEI UI yet.

Income statement now includes recorded inventory losses and gains. Added transfer integrity and tenant isolation coverage; historical lot dates cannot be changed through ordinary operations.

Serial tracking: tenant-unique serial and optional validated IMEI, existing physical stock identification, mutually exclusive with lot mode, exact serial selection required for sales, individual warehouse transfer, immutable movement history and warranty end date snapshot at sale. Refunded devices enter quarantine and require inspection confirmation before resale. No repair orders, dual IMEI, manufacturer warranty validation or serial disposal yet.

Serial UI: owner registry, search/filter by status, registration, transfer, inspection release, paginated event history including sale warranty snapshot. POS requires one distinct serial code per sold unit, with server-side validation; no automatic choice or inferred IMEI. Warranty displayed in registry/history; PDF warranty certificate and repair workflow pending.

SAV: owner-only repair intake for sold serialized devices (server-verified commercial warranty snapshot) or external devices, duplicate active device checks, custody history, diagnosis, non-binding estimate, recorded customer approval, technician assignment, controlled status transitions and confirmed handover. No stock movement from customer-owned repairs; active repair blocks linked sale refund. Closed orders/events protected against ordinary modification. Estimate does not collect money, reserve spare parts or establish legal warranty eligibility. Customer portal, repair invoice/payment and PDF certificate pending.

SAV UI: owner navigation, searchable paginated dossiers, sold-device lookup and recorded warranty, external-device intake, physical condition/accessories, diagnostic/estimate, manually recorded customer approval, assignment by staff ID, repair workflow, confirmed handover, and event history. No customer portal or actual charge collection yet.

Printable service documents: A4 reception sheet from stored SAV intake and warranty certificate from current tenant-scoped sold-device proof. Uses textContent for all business data, print/save-as-PDF via browser; no generated PDF file endpoint or signature verification. Warranty certificate deliberately excludes unsupported promises and does not create payment evidence.

Commercial documents: immutable quote snapshots priced from catalog, tenant/year/type sequence under owner lock, client approval and expiration, atomic quote conversion through existing sale transaction, one invoice and one confirmed full-delivery note per eligible actual sale. No new stock/financial entries from document issuance. No fiscal certification, VAT engine, credit note or partial delivery; refunded sales retain immutable originals and current status is shown separately.

Commercial documents UI: search clients/products, quote draft/issue/accept/cancel, explicit quote conversion into existing sale with cash/credit confirmation and optional serial inputs, invoice/delivery issuance from real sale IDs, A4 print/save PDF, immutable history and current sale status. French owner-only UI. No legal tax invoice certification or actual electronic payment integration.

Receivables: new credit sales create a per-sale balance in accounting currency; optional deposit in sale currency is converted at sale rate and credited against receivables, not revenue. Explicit due date, targeted cash payment in base currency, legacy aggregate settlement consumes unallocated historical debt first then tracked oldest due receivables. No fabricated historical per-sale allocation; payment history immutable. Full settlement changes sale status but credit refund still blocked. Customer deletion disabled to preserve history. No pre-sale deposits, payment reversals, installment schedules, FX revaluation or mobile payment verification.

Receivable UI: POS and quote conversion accept optional credit-sale deposit and due date, owner register with open/paid/overdue filters and currency-separated totals, targeted partial cash receipts and printable internal receipts. The debt screen remains for historical aggregate balances. No electronic payment provider or fiscal receipt certification.

Document details also expose current receivable balance separately from immutable document totals; POS deposit input uses selected sale currency and resets amounts on currency change. Accounting currency changes on historical balances still require a dedicated controlled migration workflow.
